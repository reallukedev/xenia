# Architecture

Xenia is one Rust engine with a native app per platform.

```
┌───────────────────────────────┐   ┌───────────────────────────────┐
│  iPhone app (SwiftUI)         │   │  Mac app (SwiftUI + AppKit)   │   Future: Android (Compose),
│  tabs, sheets, swipe to reply │   │  split view, inspector, menus │   Windows (WinUI), Linux (GTK)
└──────────────┬────────────────┘   └──────────────┬────────────────┘
               │  Swift bindings generated by UniFFI (apple/XeniaCore)
┌──────────────┴──────────────────────────────────┴────────────────┐
│ xenia-core (Rust)                                                │
│  XeniaClient ─ session, sync, room list, actions, media, search  │
│  TimelineController ─ one conversation or thread, as rows        │
│  pure rules ─ rich text, mentions, list filters, notifications,  │
│               run grouping, time headers, delivery               │
└──────────────┬───────────────────────────────────────────────────┘
               │
        matrix-sdk + matrix-sdk-ui (sliding sync, E2EE, SQLite stores, search index)
```

## The boundary

Three rules keep it clean, and they're what make another platform cheap:

1. **Data out, decisions in the core.** Records crossing the boundary are view-ready. A
   `RoomSummary` already knows its scope (Chats or Rooms), whether it's unread and how, and what
   its preview says. A `TimelineMessage` already knows its place in its run (`run.is_first`,
   `run.is_last`), whether to show the sender's name, and whether "Delivered" or "Read" hangs
   under it. If two platforms would write the same `if`, it belongs in Rust.
2. **Words stay native.** The core never builds a sentence. Previews, notes ("Maya joined") and
   errors cross as enums (`Body`, `Note`, `RoomPreview`, `XeniaError`) and each app words them
   with its own localization (`apple/Shared/Copy/`). Times cross as milliseconds and are formatted
   natively.
3. **Platform services come in through traits.** Secrets go through `SecretStore`, which the app
   implements (the Keychain on Apple platforms). The core never calls a platform API.

## Flow of data

- **Events out.** The app gives the core a `ClientListener` when it creates the `XeniaClient`.
  The core calls it from its own threads: session changes, connection state, the whole room
  list (coalesced to one call per ~24 ms burst), messages that deserve a notification, and
  backup status. The Swift side (`ClientEvents`) hops to the main thread in order and updates an
  `@Observable` model; views read the model.
- **Timelines.** Opening a conversation creates a `TimelineController` with a `TimelineListener`.
  The core mirrors the SDK's timeline diffs, rebuilds only the rows whose items changed (rows are
  cached by item identity), lays them out (`timeline/layout.rs`) and sends the complete list. The
  apps diff it by row ID: a collection view on iPhone (`iOS/TimelineCollection.swift`,
  `TimelineLayout.swift`) and a scroll view of reused rows on the Mac
  (`macOS/TimelineCollection.swift`). Rows are SwiftUI; each is measured once and its height kept
  by row ID, so older pages arriving above never move what's on screen and only changed rows
  redraw.
- **Actions in.** Everything a person does is an async call: `send`, `edit`, `toggle_reaction`,
  `mark_read`, `set_favourite`, `start_direct_chat`... Every exported async function runs on the
  core's own Tokio runtime (`runtime.rs`), so the app's executor (Swift concurrency) never needs
  to know about Tokio.

## Why the whole list, not diffs

The room list and timelines cross as full snapshots rather than diffs. A few hundred records
serialize in well under a millisecond, SwiftUI diffs by identity anyway, and it removes a whole
class of bugs (a missed diff leaving the UI out of sync forever). If a platform ever needs diffs,
they can be added beside the snapshot without changing the rows.

## Push

Pushes carry only a room and an event ID (`event_id_only`), so neither the gateway nor Apple sees
content. The Notification Service Extension (iPhone, and team-signed Mac builds) opens the app's
stores from the App Group container with its own cross-process lock holder
(`Process::NotificationExtension`, "nse"; the app is "main"), fetches and decrypts the event with
the SDK's `NotificationClient`, and words it with the same `NotificationContent` the app uses.
`NotificationExtras` then makes it a communication notification (the sender's photo, an
`INSendMessageIntent`) and attaches any photo. The session's secret lives in a Keychain access
group they share.

On iPhone, pulling a notification down opens the content extension (`NotificationConversation`,
lock holder "nce"): it asks the server for the room's latest messages through the same
`PushDecoder` and sends replies itself, handing them to the app only if sending fails.

Every homeserver pushes to one gateway, `services/push-gateway` on Vercel
(`xenia-push-gateway.vercel.app`), which holds Xenia's APNs key and forwards to Apple. Builds
installed from Xcode register as `dev.xenia.matrix.ios.dev` / `.mac.dev` (sandbox), TestFlight
and App Store builds as `dev.xenia.matrix.ios` / `.mac` (production), read from the signature;
the simulator uses `scripts/dev/push-gateway.mjs`.

Reading a conversation on another device makes the homeserver send a push with only the new
unread count. The gateway turns it into a badge update plus a silent background push
(`xenia_read`), which wakes the iPhone app for a few seconds of sync: notifications of
conversations read since they arrived leave Notification Center (`Notifier.clearRead`). iOS
throttles background pushes and skips them for an app swiped away, so the same sweep also runs on
the first room list after Xenia comes to the front.

The homeserver pushes every group message its rules allow; the device narrows that with
`effective_mode` (public rooms and, with the Rooms setting off, all groups notify only for
mentions unless a room has its own mode). Without Apple's filtering entitlement the extension
can't drop a push, so such pushes land quietly (passive, no sound). `XENIA_CAN_SILENCE_PUSHES`
switches to dropping them once the entitlement is granted.

On the Mac, Xenia also keeps syncing with its windows closed and notifies from the running app,
which covers local debug builds (signed to run locally, so without push or the App Group). When
push is registered and Xenia isn't in front, the app waits a few seconds and stays quiet if a push
already showed the message. "In front" comes from AppKit (active app with a main window showing),
not the window's scene phase, which never updates once the window closes.

The first team-signed Mac build to run moves the stores from the app's container into the App
Group, as the iPhone did; older Mac builds can't find them afterwards.

## Storage and secrets

Each account gets a folder under the app's data directory with the SDK's SQLite stores (state,
crypto, event cache) and the search index, all encrypted with a random 32-byte passphrase. The
passphrase and the session tokens live in the platform's secret store under one key
(`xenia.session.v1`). Signing out deletes the folder and the secret.

## Building

`scripts/apple/build-core.sh` runs as the first build phase of the `XeniaCore` framework. It
builds the static library for the platform Xcode is building (in a clean environment, so Xcode's
SDK settings can't leak into Rust build scripts), and regenerates the Swift bindings only when the
library changed. The apps link `target/<triple>/<profile>/libxenia_core.a`. Debug builds use the
`dev` profile with optimized dependencies (crypto and SQLite are slow unoptimized); release
builds use thin LTO.

## Tests

- `cargo test -p xenia-core`: every pure rule (rich text, mentions, emoji, snippets, list
  filters, unread state, notification decisions, run grouping, headers, note folding, delivery,
  error classification, server addresses).
- Swift Testing (`apple/Tests/`): the app's words (`Copy`, `SettingsCopy`, `TimeFormat`), the
  session gate at sign-in, mention suggestions, poll votes, attachments, BlurHash, iCloud settings
  sync and the iPhone timeline layout.
- `node --test` in `services/push-gateway`: payloads, APNs environments, provider tokens and
  which failures drop a pusher.
- CI (`.github/workflows/ci.yml`) runs rustfmt, clippy and the core's tests on Linux, the push
  gateway's tests, and a build of the Mac app.
